# Phase 2A completion report (2026-11-02)

Status: **implemented, tested and demonstrated on SQLite and on a local PostgreSQL 18.4 server.** Phase 2B has not been started.

**Change of 2026-11-03: the validation step was removed** at the project owner's request. The flow is now: a person uploads a photograph, the AI gives its verdict, the person supports it or disregards it, and in either case writes the reasons in the reason box (compulsory, 2026-11-03 later the same day: even when they agree, because the AI may have missed real points). That submission is final and is the validation. Sections below describe the system as it now is; migration 0002 carries the change. Earlier text about validators, four-eyes validation and "approve for learning" no longer applies.

### Frontend
A dependency-free review screen served by the same service (there was no existing frontend or dashboard to extend). Photo list with upload; review screen with the photograph, AI recommendation, quality, warnings, tabs for gates (failed / uncertain / soft / passed / not applicable, each with the AI's evidence), scene, quality, publication and tags; per-item "Correct" with reason checkboxes and comment; queue and save; add or remove a tag; "Support the AI" or "Disregard the AI" with a reason box (required when disregarding); a red confirmation box for publication blockers. There are no validator controls. All data is inserted as text, never as markup; a Content-Security-Policy forbids inline script and style. Checked visually in the browser pane (login, list, review, correction form, queue, missing-reason message); the save and submit paths are covered by the API tests.

**Mutation checks** (a safety rule broken on purpose, then the suite run): 13 distinct rules checked, all caught by a failing test: organisation scoping in three getters, AI value from the client, idempotent replay, deactivated user still accepted, evaluation re-write allowed, policy-change exclusion, disregarding the AI without a reason, triggers not installed, example active for retrieval; after the simplification also the reason requirement (removed, and inverted), the policy-change exclusion and the publication-blocker rules. **Demonstration** (`scripts/demo_phase2a.py`): scenarios A to G run through the HTTP API on four real photographs and the answers the engine already produced for them in pilot 3. No model was called.

## 3. Security controls
Scrypt password hashing; JWT (HS256, 8 h) with the user re-read from the database on every request, so deactivation takes effect at once; role checks (REVIEWER, ORG_ADMIN); organisation scoping on every query with 404 for foreign records; login rate limit per account and address with an identical answer for unknown account and wrong password; upload limits, decoding check and content-addressed storage with path-traversal protection; no image bytes, passwords or key material in logs or errors (a secret-looking string in an evaluator error is removed before storage); security headers and CSP; photographs served only to authenticated members of the owning organisation with `no-store`; the real evaluator fails closed without `NGO_ALLOW_CLOUD_INFERENCE=true` and a key. No secret is in a file; `.gitignore` excludes databases, storage and demo data (the demo database holds client photographs).

## 4. Known limitations
1. **PostgreSQL verified on a local test server (2026-11-03), not on a production-like deployment.** Against a throwaway PostgreSQL 18.4 on this machine: `alembic upgrade head`, `downgrade base`, `upgrade head` all succeed (11 tables, 12 triggers, partial unique index, 4 composite foreign keys); `alembic check` reports no drift between models and migration; all tests pass on PostgreSQL both with `create_all` and with the schema built by the migration (`TEST_USE_ALEMBIC=1`); disabling the evaluation-freeze trigger makes a test fail on PostgreSQL. One real bug was found and fixed (the trigger function used a `%` that psycopg 3 treats as a placeholder, so the migration failed on a real server). Not yet covered: PostgreSQL 13/15/16, a managed cloud instance, concurrent load, and backup/restore.
2. **Evaluation runs inside the web process** (a background task). A restart loses in-flight work; `fail_stale_runs` closes such runs as FAILED (never approved) and the photo can be re-evaluated, but a real queue (and `LangGraph` or similar, if the workflow grows) is a later step. One evaluation takes about a minute.
3. **No retention or deletion workflow.** Photographs, evaluations and events cannot be deleted by design (audit). A lawful deletion or anonymisation process for children's images is required before deployment and needs a deliberate, logged exception to the triggers.
4. **Login rate limiter and JWT secret are single-instance.** Several instances need a shared limiter; there is no token revocation other than deactivating the user, no refresh tokens, no multi-factor authentication.
5. **Local-disk object storage.** The interface is ready for a cloud bucket; it is not implemented. Images are not encrypted at rest by the application (use encrypted volumes or bucket encryption and TLS in front of the service).
6. **Learning examples are only created, never used.** They are inactive for retrieval; activation, retrieval and analytics are Phases 2C and 3.
7. **Nothing checks a decision against the rules but the person who makes it.** With the validation step removed (2026-11-03, at the project owner's request) a single reviewer's decision is final. Mistakes are limited by the written reason required when disregarding the AI, the publication-blocker statement, and the exclusion of `POLICY_CHANGE` / `HUMAN_REVIEW_ERROR` reviews from learning; the system cannot tell whether a decision contradicts a mandatory NGO rule. Every supported or disregarded verdict becomes a learning example, so a reviewer who rubber-stamps the AI would add agreeing examples; examples are inactive until Phase 2C, which should decide how to weight or sample them.
8. **The review screen is plain JavaScript.** It was built without a framework because the project has no frontend; it can be ported to React later. It has not been tested on mobile or with a screen reader.
9. **The default registered evaluator is V1.** V2 is registered as a DRAFT: five of its seven changes conflict with NGO decisions of 2026-11-02 and it raised false approvals in the pilot (`layered-engine/docs/V1_V2_COMPARISON.md`). It can only be run as an administrator's labelled experiment.
10. The layered engine still reports "policy changes not approved by the NGO" for V1 (its `PROPOSED` items, such as the G001 component split and soft G010/G011); the review screen shows this as a notice.
11. **Approving over a publication blocker (added 2026-11-03 after the Phase 2A review).** The review found that nothing stopped a person approving a photograph whose evaluation listed a blocker such as a legible number plate (`decision_output.publication.blockers`). Now `submit_review` refuses an APPROVE unless it carries a written statement of at least 15 characters; the API field is `publication_blocker_statement`; a rejection never needs one. The statement and the blockers as they were are recorded in an append-only `BLOCKER_ACKNOWLEDGED` event (no schema change), and the review screen shows a red box with a "have read" tick and a text box, and afterwards "Approved despite publication blockers" with the statement. Five tests cover it (refusals write nothing, the record, rejection and no-blocker paths, low-confidence flags are not blockers, retry safety); three deliberate breakages of the rule were each caught. Such an approval never becomes a learning example, because it rests on what happens to the photograph before publishing rather than on what it shows. Open choice for the NGO: whether such an approval should need a second person instead of one statement (with the validator role removed, there is nobody to ask). Under V1 a blocker already makes the engine recommend HUMAN_REVIEW, so the AI never approves over a blocker; the rule does not depend on that.
13. **Migration chain was broken after the first version (fixed 2026-11-03).** Earlier in this report the migration was described as verified up and down; that was true of 0001 alone. Each later migration installed every current immutability trigger, including those of tables that did not exist yet at that revision, so a fresh upgrade through 0001 or a downgrade would fail; and the 0002 downgrade failed on SQLite (an unnamed foreign key). Found when 0003 was added. Each migration now installs only the triggers of the tables that exist at its revision, and `tests/test_migrations.py` walks every revision up and down one step at a time on SQLite and PostgreSQL and checks the trigger count at each. Every new migration adds its tables to the same lists in `triggers.py` (done for 0003 and 0004). 0003 adds `photo_embeddings`, `example_flags` and `evaluation_runs.few_shot` for the example store (docs/PHASE3_LEARNING_LOOP_DESIGN.md, section 13).
12. **Static files were cached by the browser (fixed 2026-11-03).** `/static` had no `Cache-Control`, so a browser could keep running an old `app.js` against an upgraded API; it now sends `no-cache` (revalidate by ETag on every load) and a test checks it.

## 5. Dependencies for Phase 2B (historical enrichment)
* Decide where the 4,000 historical photographs live: Phase 2B should import them as `photos` of a dedicated organisation (or a flagged historical collection) and write their enrichment as new tables (`annotations`, `tag_taxonomy`, `tag_mappings`), keeping `historical_decision` in its own table, never in `evaluation_runs`.
* Reuse `execute_evaluation` with the engine's HISTORICAL_ANNOTATION mode (labels hidden); needs a batch runner with resumability and a cost cap (the engine already has both), and a real price for `gemini-3.8-flash` (still a placeholder).
* PostgreSQL verification (item 1) before loading 4,000 photographs.
* The NGO's decisions on the open policy questions (face scope, gaze, banner, back view) determine which rulebook version the enrichment uses; annotating 4,000 photographs with a rulebook the NGO may change is the main risk to avoid.
* A named human on the NGO side to check a sample of the historical enrichment (this is Phase 2B's own check, separate from the removed per-review validation).
